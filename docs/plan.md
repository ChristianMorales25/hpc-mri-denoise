## Experiments (maps to the course's "Common Requirements")

- **Runtime / speedup / efficiency**: seq vs OpenMP vs CUDA for each filter.
- **Strong scaling**: fixed volume, OpenMP threads 1, 2, 4, 6, 8, 12.
- **Weak scaling**: synthetic volume size grows with thread count
  (constant voxels per thread).
- **Problem size**: 64³, 96³, 128³, 181×217×181 (BrainWeb), 256³.
- **GPU configuration**: block shapes, shared memory on vs off.
- **Memory-transfer cost**: H2D/kernel/D2H split, and how it shrinks
  relative to compute as the work per voxel grows (bilateral → NLM).
- **Quality**: PSNR/SSIM vs noise level (3–9 %) and filter parameters; Dice
  of the downstream segmentation with and without denoising.
- **Correctness**: every parallel version checked against the sequential
  baseline (`evaluate.py --ref`).

## NLM GPU optimization ladder (BrainWeb noisy_5, Oct 28)

Kernel time, median of 3, block 8×8×4 (`scripts/nlm_variants.sh`).

| Setting | naive | smem | sep v1 | sep v2 |
|---|--:|--:|--:|--:|
| S=3, P=1 | 516 ms | **211 ms** | 342 ms | 249 ms |
| S=3, P=2 | 2960 ms | 1034 ms | 615 ms | **386 ms** |
| S=5, P=1 | 2287 ms | **943 ms** | 1485 ms | 962 ms |

- **smem**: tile + (S+P) halo in shared memory, same arithmetic as naive and
  bit-identical output. 2.4–2.9× over naive.
- **sep**: per offset, squared differences over the tile, then three 1D box
  sums in shared memory (3 barriers per offset). Matches naive within 1e-6.
  v1 recomputed shared-memory indices with integer div/mod every offset;
  v2 precomputes them once per thread, which cut 27–37 %.
- With 3×3×3 patches the separable trick saves too little arithmetic to beat
  its barriers and halo work, so smem and sep tie. With 5×5×5 patches sep is
  2.7× faster than smem and 7.7× faster than naive, as expected from
  O(P) vs O(P³) work per offset.
- Block sweep at S=3 P=1 (`scripts/nlm_block_sweep.sh`, results in
  `results/nlm_blocks_S3P1.csv`): smem is flat across shapes (220–234 ms);
  sep prefers compact blocks (8×8×4 best, 250 ms) because flat blocks
  (e.g. 32×8×1) spend most of the D/B passes on the z-halo.

Ideas if more NLM speed is needed: fuse the x/y box passes to drop a barrier;
exploit weight symmetry w(x, x+s) = w(x+s, x) to halve the offsets.

## Bilateral and diffusion GPU optimization (BrainWeb noisy_5, Nov 3)

Kernel time, median of 5 (`scripts/gpu_ladder.sh`, `results/gpu_ladder.csv`).
Every variant matches OpenMP within 5.5e-6 over all block shapes, fusion
depths, and z chunks tested (`scripts/check_variants.sh`, 56 configurations).

| Kernel | naive | cuda-smem | cuda-fused (K=2, 32×16) |
|---|--:|--:|--:|
| Bilateral r=2 | 4.96 ms (best block) | **3.89 ms** (1.3×) | |
| Bilateral r=3 | 13.96 ms | **9.12 ms** (1.5×) | |
| Diffusion 20 it | 6.86 ms | 14.24 ms (0.5×) | **6.08–6.61 ms** (1.1–1.2×) |

- **Bilateral smem**: one global read per tile voxel instead of (2r+1)³ per
  output, spatial weights from constant memory. The gain grows with r (more
  reuse per loaded voxel); at r=2 the L1 cache already catches most of it.
- **Diffusion is bandwidth-bound**: the naive kernel moves ~160 GB/s, close to
  the RTX 4050 Laptop's peak, so only less traffic can help.
- **3D shared-memory tile is a negative result** (2× slower): an 8×8×4 block
  with a 1-voxel halo loads 600 voxels to update 256, more traffic than the
  naive kernel, whose neighbor reuse the caches already capture. A first fused
  version that also used 3D tiles (K-voxel halo in x, y, and z) was 3–15×
  slower than naive for the same reason, plus the redundant halo updates.
- **2.5D z-marching + temporal blocking** (`cuda-fused`): one thread per x-y
  column, each iteration level keeps a 3-plane ring buffer in shared memory,
  so K iterations are pipelined along z with no z halo. Prefetching the next
  plane into a register before computing the current one hid the load latency
  (K=1 went from slower than naive to equal). K=2 is best; K≥4 loses to the
  x-y halo redundancy (output tile (32−2K)×(16−2K)) and the K+1 barriers per
  plane. Longer z chunks help (zc 8 → 0: 12.8 → 8.5 ms at K=4).
- **Problem size decides whether fusion pays** (`scripts/diffusion_sizes.sh`,
  `results/diffusion_sizes.csv`): up to 128³ (8 MB per buffer) the data stays
  in L2 and naive wins; from 192³ up it is DRAM-bound and fused K=2 wins by
  1.17–1.38× (192³ 7.85 → 5.70 ms, 256³ 16.96 → 14.50 ms).

Ideas if more diffusion speed is needed: compute each face flux once and
share it between the two voxels (halves the exponentials); register-blocked
z-marching without shared memory for the z neighbors.

## Known caveats to discuss in the report

- Whole-volume metrics are dominated by background, where Rician noise has a
  non-zero mean that no filter here removes; tissue-masked metrics are the
  primary ones.
- Laptop GPU: thermal throttling and the ~2 s TDR kernel limit under WSL2.
- `--use_fast_math` on the GPU gives differences around 1e-6 from the CPU.
